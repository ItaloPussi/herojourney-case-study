Engineering a Personal Operating System.

Herojourney is a domain-driven system for turning long-term intentions into daily action and recorded evidence — while preserving the difference between plans, commitments, outcomes and historical truth.

01 · THE PROBLEM

Most productivity tools flatten meaning.

A task, a commitment to a date, evidence that something happened, and a retrospective conclusion are not the same thing.

Herojourney models these concepts separately, so changing today's plan does not silently rewrite what yesterday meant. That principle influences the domain model, persistence, exports, review workflows and cross-module integration.

Preserve the semantic difference between intention, commitment, evidence, outcome and memory.
02 · PRODUCT

A real product, not an architecture exercise.

The domain model is exercised through daily workflows: plan, commit, record evidence, review what happened and decide what changes next.

Select any screen to inspect it at full resolution.

03 · ARCHITECTURE

Boundaries first. Frameworks second.

04 · ENGINEERING DECISIONS

Trade-offs documented as part of the product.

The repository treats architecture as an executable constraint, not a slide deck.

01

Modular monolith over premature services

Each module owns its data, rules, routes and persistence access. Cross-module behavior is exposed through explicit seams.

02

Events for facts; providers for current state

Typed events represent something that happened. Dynamic Context providers answer current-state questions.

03

Historical meaning is preserved

Snapshots preserve relevant context so today's edits do not silently redefine yesterday.

04

Versioned analytical exports

Immutable schemas, deterministic ordering and pseudonymous references instead of raw persistence IDs.

05

Single-node operations by design

Docker Compose, SQLite, immutable images and explicit backup/rollback behavior keep operations deliberately small.

06

AI-assisted development with guardrails

Coding agents operate inside documented boundaries, maintainability limits, architecture checks and CI requirements.

05 · SECURITY ENGINEERING

Security is implemented in the edges.

01

SSRF-aware external feed ingestion

HTTPS-only URLs, credential rejection, DNS checks, private/reserved address blocking, redirect constraints and bounded response bodies.

02

Privacy-aware analytical export

Raw persistence IDs stay private. Stable references are pseudonymized and scoped while schemas validate the complete export.

03

Explicit authentication boundary

Application profile identity remains distinct from authentication identity and domain ownership.

04

Deployment integrity and rollback

Backups are verified before schema changes, images are digest-pinned and failed deployments restore data and previous image references.

08 · TAKEAWAY

The interesting part is not the number of modules. It is the precision of the boundaries.

Herojourney is an ongoing experiment in turning product semantics into enforceable architecture: preserving historical truth, keeping module ownership explicit, and operating the system with enough rigor that automation can move quickly without eroding the model underneath it.
